Jaime · 2026-05-13 · BC-7065 · proposed

User lifecycle — offboarding + re-activation + mid-season role change

Net-new flow on top of BC-3123. Season-end offboarding: soft-deactivate (not hard delete) preserves all progress data — the ~24 confirmed 2026 returners come back next season with their prior progress intact. Bulk deactivation runs at season close (TM-triggered, per-territory). Re-activation flow reuses the same invite mechanism but skips already-completed modules. Mid-season role change (JT → ST promotion) preserves completed modules and auto-enrolls in the delta of the new track (pairs with BC-7055 when it lands in M02). Auto-expires any pending invitation tokens belonging to deactivated users.

Resolves Jaime's question 4. Brite is fundamentally seasonal — 75% completion / 40% return rate per the retention playbook baseline. Without a real offboarding flow, the admin UI either accumulates stale users forever or loses returner progress every January. Soft-deactivate is the only design consistent with the returner economics.

Jaime · 2026-05-13 · BC-7066 · proposed · docs

Authoring runbook — how an admin builds a training

Documentation, not a feature. Brite LMS is Git-as-CMS: modules live as markdown in the handbook repo, tracks are configured in tracks.json, quizzes are YAML alongside the module. There is intentionally no in-app WYSIWYG authoring UI. The runbook documents the four-step authoring path: (1) write module markdown with frontmatter, (2) add to tracks.json + modules.json, (3) write quiz YAML, (4) commit + PR. BC-6604 CI guard catches broken track-slug refs. BC-7003 edit-on-GitHub footer is the in-app jump point. Runbook linked from the admin nav under "Authoring".

Resolves Jaime's question 5. The intuition that this needs docs not features was right — the architecture choice is deliberate (handbook is the single source of truth; an in-app editor would create drift). A 1-2 page runbook closes the discoverability gap for new admins.
